# Batch 1: Agent Observability and Runtime Snapshots

## Status

Implementation branch: `feat/batch-1-agent-observability`

This document records the implementation boundary and measurement semantics for
MarketTwin Batch 1.

## Core invariant

MarketTwin observes and supervises the run. Google ADK continues to own each
Persona Agent's autonomous multi-turn reasoning/tool loop.

Batch 1 does **not** turn Persona Journeys into scripted Python orchestration or
one-shot LLM calls.

## What Batch 1 adds

### Immutable historical agent snapshots

A model-backed runtime stores the effective configuration that actually ran:

- stable role and runtime name;
- runtime/framework kind;
- model provider/name and safe settings;
- agent/template version;
- effective instruction;
- initial runtime prompt;
- generated Persona and Mission where applicable;
- literal success criteria;
- tools actually exposed to the Persona;
- policy references;
- deterministic SHA-256 of the semantic snapshot.

The persisted snapshot is historical truth. The UI must not reconstruct an old
run from the repository's current prompt/template.

### Model invocation ledger

Each observable model invocation/attempt can record:

- TestRun/Journey/Execution/snapshot identity;
- role and runtime invocation identity;
- requested model and provider;
- start/completion time and latency;
- status/error class;
- input, cached-input, output, reasoning, tool-prompt, and provider total
  token fields where the runtime exposes them.

Unknown values stay NULL/unknown. MarketTwin does not convert missing usage into
zero.

## Google ADK integration

ADK 2.5.0 exposes `before_model_callback`, `after_model_callback`, and
`on_model_error_callback` on `LlmAgent`. Batch 1 uses those callbacks only
for observation and persistence.

The callback returns remain `None`, so ADK keeps normal model/tool/model
continuation.

ADK's `LlmResponse` exposes
`GenerateContentResponseUsageMetadata`. The normalized fields used by
MarketTwin are:

- `prompt_token_count` → input tokens
- `cached_content_token_count` → cached input
- `candidates_token_count` → output
- `thoughts_token_count` → reasoning
- `tool_use_prompt_token_count` → tool-prompt usage
- `total_token_count` → provider/runtime total

The ADK LiteLLM adapter maps LiteLLM usage into this metadata.

Provider-internal retries performed inside an ADK/LiteLLM call are not claimed
as independently observed attempts when the runtime does not surface them.
The invocation row records that limitation in metadata.

## Visual Verifier integration

The Visual Verifier remains a targeted direct LiteLLM call, not an autonomous
agent.

Its explicit MarketTwin rate-limit retry loop is observable, so each explicit
attempt is recorded independently. LiteLLM usage is normalized from the
OpenAI-style response fields when available.

A provider/runtime can omit cached-token detail. In that case MarketTwin
preserves it as unknown instead of fabricating a value.

## API

Authenticated TestRun-scoped endpoints:

- `GET /api/v1/test-runs/{test_run_id}/agents`
- `GET /api/v1/test-runs/{test_run_id}/agents/{snapshot_id}`
- `GET /api/v1/test-runs/{test_run_id}/usage`

The same workspace/TestRun access pattern used by existing evidence/results APIs
is applied before observability data is returned.

## UI

The TestRun now has an **Agents** tab.

For each historical runtime it can display:

- role, Persona and Mission;
- model/framework;
- model-call/token summary;
- unavailable-usage warning;
- exposed tools;
- exact effective instruction;
- initial runtime prompt;
- immutable runtime YAML;
- model invocation rows.

The YAML is rendered deterministically from persisted snapshot data. It is not
generated by the LLM and does not grant execution authority.

## Security

Snapshots and telemetry must not contain:

- passwords, OTP/MFA values, CAPTCHA answers;
- card/payment information;
- cookies or browser storage;
- authorization headers/API keys;
- private takeover keystrokes;
- signed artifact URLs.

Model configuration snapshots intentionally exclude credentials.

Prompts/YAML are descriptive historical data. They cannot expand target
authorization, disable sensitive-input policy, or grant purchase/payment
authority.

## Out of scope for this batch

Batch 1 intentionally does not change:

- Persona count or Mission assignment;
- Study Contract;
- agent memory/context compiler;
- budgets/model routing;
- HITL;
- browser authority/lifetime;
- criterion evaluation semantics.

Those are later batches.
