## Product decisions governing the seven stages

The intended user has shipped a UI and must decide what to change before their next release. The result should help them choose a change, locate it, explain why it matters, and verify the repair on their next run. Treat that as the success condition for the visual audit. The stages below are one implementation sequence.

### What the customer should experience

1. **At Start**, show the submitted URL, desktop scope, selected mode and any attached brand or product guidance. A URL alone is sufficient. Explain what a ten-minute report covers. If authentication limits access, offer takeover at the blocked step and make public coverage available.
2. **During Watch**, show the first supported observation, sections reached, states exercised and current work. For example, distinguish “Product switch found” from “Switched to Agent and verified the content changed.” Show progress even when the selected browser lane is idle. Use counts while discovery is expanding.
3. **At Results**, answer “What should I change first?” Each recommended change needs a location, consequence, evidence, and a repair the user can verify. For a hypothetical clipped action, show the annotated control, the viewport and a check such as “Open the panel at 1280px and confirm the full action label remains visible.” For MT-000206, show the shared typeface and repeated labels under design observations only if they explain something specific about this page. If no supported fix emerges, lead with the checked scope and its gaps. Avoid manufacturing a top-three list.
4. **On the next run**, compare the same component, state, viewport and access context. Mark a previous issue resolved only after the relevant check executes with a passing outcome. If the page was skipped, blocked, or substantially changed, show why comparison is unavailable. Keep the original evidence and rule version with each historical result. Build this comparison once stable identities and rerun evidence exist.

### How design judgment earns trust

| User question | Evidence required before answering |
|---|---|
| Does my interface feel unified? | Compare equivalent components and roles across observed pages or states. Show both examples, the specific difference and any relevant exception, such as a destructive action or selected state. Attached design guidance can establish intent when it cites the relevant passage. |
| What feels generic? | Point to the actual copy, imagery, layout or repeated treatment, explain the impression in context and offer a concrete alternative tied to the product. Label it as design judgment. A claim about resemblance to other products needs a documented reference set. Visual appearance alone cannot establish who built a page. |
| Can people use it? | Cite measured legibility, focus, clipping, ambiguous labels or a recorded interaction with an observed outcome. Keep a persona's goal and constraints visible when making a persona-specific claim. |

### How to choose an efficient operating point

Use the existing four-lane run as a baseline. Replay equivalent workloads at fixed scope and change one scheduling or review decision at a time. Choose the lowest-cost configuration that preserves discovery of seeded important defects, meets the latency target on the stated workload and maintains precision on unseen sites. Track the slowest cases alongside the median, including elapsed queue and evaluation time. Also record browser-seconds, tokens and retained bytes per run. A faster configuration that skips the only broken menu fails the comparison.

Spend early time on distinct user journeys and component families. Reserve a reproducible sample of low-risk pages for independent inspection so missed exceptions inside repeated templates can be measured. Expand sampling when those checks uncover differences. Publish the inspected sample and remaining inventory. The ten-minute target is a deadline for a usable report. The supported size for complete coverage must come from measured runs. Use per-run evidence reuse first. Reuse findings across releases only when a fresh check supports the claim.

### How to prove customer value over time

At stage 5, give representative builders an unfamiliar report and ask them to pick their first change without coaching. Record whether they choose a supported issue, can locate it, and understand what remains unchecked. At stage 7, have them apply the repair on an owned fixture, rerun and interpret the outcome. Measure time to a verified repair, misleading recommendations and missed important issues. Keep disagreements and clean examples in the labeled regression set. For each later rule, model or prompt change, replay the baseline and a separate held-out set, compare by issue family and site type, and retain the previous version if quality regresses. Record sample sizes and unresolved disagreements. The historical example runs motivate this work. Customer value and general accuracy remain to be demonstrated.
